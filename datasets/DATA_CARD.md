# Inforsight Fictional Policy-Event Sample — Data Card

## Dataset summary

This dataset is a small, deterministic sample of completely fictional life-insurance policy-event histories generated by Inforsight's clean-room simulator. It exists so reviewers and developers can inspect the versioned event contracts, multi-event lifecycle paths, history validation, serialization, and replay inputs without generating the full development corpus.

The sample contains no customer records and is not de-identified, anonymized, or derived from real insurer data. Every identifier, date, amount, product variant, event, and outcome was created by original repository code.

## Artifact inventory

- [`sample-policy-events.jsonl`](sample-policy-events.jsonl) contains one complete policy event per line. Histories remain contiguous and events retain deterministic generator order.
- [`sample-manifest.json`](sample-manifest.json) records versions, generator inputs, the selection rule, composition counts, and the dataset digest.

The applicable event envelope and payload definitions are in [`../data-contracts/`](../data-contracts/). Cross-event lifecycle and temporal rules are documented in [`../simulator/README.md`](../simulator/README.md).

## Intended uses

This sample is suitable for:

- Manual inspection of fictional policy-event envelopes and nested payloads.
- Demonstrating coherent multi-event histories for all current simulator scenarios.
- Exercising JSONL parsing, contract validation, history validation, and point-in-time replay.
- Reproducing documentation examples and repository tests.
- Reviewing clean-room and deterministic-generation practices.

## Unsuitable uses

Do not use this sample for:

- Customer, policy, pricing, underwriting, conservation, or communication decisions.
- Estimating lapse, surrender, payment-failure, product, or service-contact prevalence.
- Actuarial, financial, operational, demographic, or market inference.
- Training, validating, or benchmarking a predictive model.
- Measuring model accuracy, calibration, ranking quality, fairness, or business value.
- Inferring a real insurer's products, rules, timing, workflows, or customer behavior.
- Claiming production readiness or real-world representativeness.

Its small size and deliberately balanced scenario construction make it especially unsuitable for statistical conclusions.

## Generation and selection

The publication procedure is deterministic:

1. Generate the canonical 100-policy corpus using seed `20260817` and the fixed simulation start.
2. Classify each complete history from its structured event sequence as active, recovered, lapsed, or surrendered.
3. Select the first two histories from each scenario in generator output order.
4. Preserve all events from every selected history in generator serialization order.
5. Serialize with the simulator's stable JSON Lines serializer.
6. Compute composition counts and the SHA-256 digest from the resulting bytes.

No event is sampled independently, rewritten, or hand-edited. The selection rule identifier in the manifest is `first-two-complete-histories-per-scenario-in-generator-order`.

To verify the checked-in files without changing them:

```bash
python3 scripts/build_sample_dataset.py --check
```

To intentionally regenerate both artifacts after an approved generator, schema, selection, or dataset-version change:

```bash
python3 scripts/build_sample_dataset.py --write
python3 scripts/build_sample_dataset.py --check
```

Write mode replaces the two generated artifacts. Review their complete diff and update this data card whenever the artifact, manifest, or documented composition changes.

## Format and fields

Each JSONL line is one JSON object conforming to `data-contracts/policy-event.schema.json` and its event-specific payload schema. The envelope contains:

- Schema version, event ID, policy ID, and event type.
- Occurrence, effective, and ingestion timestamps.
- A strictly structured event-specific payload.

Refer to the versioned schemas rather than treating this summary as a substitute contract. Relationships across events—such as lifecycle transitions, payment-to-billing references, terminal outcome pairs, and impossible dates—are checked by the simulator history validator.

## Validation and quality checks

Repository verification establishes that:

- Every line parses as one JSON object.
- Every event passes the current envelope and payload schemas.
- Events form eight complete, single-policy histories.
- Every history passes `validate_policy_history`.
- Policy and event identifiers are unique where required.
- All four scenarios, all nine event types, and both product variants are present.
- Manifest counts equal counts computed from the artifact.
- The manifest digest equals the exact dataset bytes.
- Clean repeated generation produces byte-identical JSONL and deterministic manifest content.
- Prohibited personal, credential-like, and unstructured customer fields are absent.

Run the focused and full checks from the repository root:

```bash
source .venv/bin/activate
python3 -m unittest discover -s simulator/tests -p 'test_published_dataset.py' -v
make check
git diff --check
```

Contract-valid means each event satisfies the repository's declared schema. History-coherent means the events satisfy the current cross-event rules. Deterministic means declared inputs reproduce identical bytes. None of these properties establishes real-world accuracy or representativeness.

## Known limitations and assumptions

- Scenario weights are equal fictional test inputs rather than calibrated rates.
- Only four bounded lifecycle scenarios and nine event types are represented.
- Billing intervals use simplified fixed day counts.
- Generated ingestion occurs one hour after occurrence.
- Corrections, supersession, retractions, and complex late-arriving events are absent.
- Effective-time replay does not answer what was known at an ingestion-time cutoff.
- Lapsed and surrendered are terminal in the current MVP; reinstatement is absent.
- Notices and service contacts contain structured categories without message text.
- Amounts, methods, reasons, timing, product selection, and contact occurrence are invented engineering inputs.
- The sample is intentionally too small and coverage-oriented for model development or statistical evaluation.

Additional durable assumptions are documented in [`../docs/assumptions.md`](../docs/assumptions.md).

## Clean-room, privacy, and licensing

This artifact follows the repository's [`clean-room policy`](../docs/clean-room-policy.md): it uses original code and fictional structured data, without customer information, credentials, proprietary insurer material, or copied operating procedures.

## Maintenance and versioning

The dataset version is independent of the event-schema and generator versions.

- Increment the dataset version when selected histories, the selection rule, ordering, or serialized bytes intentionally change.
- Regenerate and review the dataset when generator or schema changes affect its output or validity.
- Update the manifest, composition tables, digest, limitations, and verification evidence together.
- Never hand-edit the JSONL artifact or manifest to make verification pass.
- Preserve old versions through Git history rather than committing multiple large generated corpora without a demonstrated consumer.

The Phase 1 [synthetic-rate assessment](../docs/experiments/phase-01-07-synthetic-rate-assessment.md) excludes this balanced sample from estimation and retains the canonical equal scenario mix as a coverage fixture. It found no directly comparable public measure that justified changing the generator or published artifacts. The sample remains uncalibrated and non-representative.
